# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그것이 우선**한다. 이 파일은 **기본값(fallback)** 이다. 충돌하는 항목만 프로젝트 규칙을 따르고, 나머지는 이 파일을 따른다.

## 1. 적용 기준

### TDD 필수

- **비즈니스 로직**: 조건 분기, 계산, 상태 전이
- **API**: 핸들러, 요청/응답 처리, 에러 매핑
- **유틸 함수**: 문자열/데이터 변환 등 순수 함수
- **버그 수정**: 버그를 재현하는 실패 테스트를 먼저 작성한 뒤 고친다

### TDD 불필요

- **타입 정의**: `type`, `interface` 선언
- **설정 파일**: `package.json`, `tsconfig`, `vite.config` 등
- **순수 UI**: 로직 없이 마크업/스타일만 있는 컴포넌트
- **SQL**: 스키마, 마이그레이션, 단순 쿼리

판단이 모호하면 **TDD를 적용한다**.

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류, 환경 문제로 인한 실패는 RED가 아니므로 먼저 고친다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 테스트를 고친다.

### GREEN: 최소 구현

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 기능, 옵션, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는 것을 실행해서 확인한다.

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지**한다. 변경할 때마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 다룬다.

### 반복

다음 동작에 대해 **RED로 돌아간다.** 모든 요구 동작이 끝날 때까지 반복한다.

## 3. 삭제 강제 규칙

테스트보다 프로덕션 코드를 먼저 작성했다면:

1. **그 코드를 삭제한다.**
2. RED부터 다시 시작한다.

**"참고용"으로 남기는 것도 금지**한다. 주석 처리, 별도 파일 보관, 복사해 두고 보면서 다시 쓰기 모두 포함한다. 코드를 보면서 쓴 테스트는 구현을 따라가는 테스트가 된다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 30초면 쓴다. 단순한 코드가 가장 자주 조용히 깨진다. |
| "나중에 테스트 추가하겠다" | 나중에 쓴 테스트는 구현에 맞춰진다. 처음부터 통과하므로 아무것도 검증하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. 급할수록 사이클을 지킨다. |
| "삭제하면 낭비다" | 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. |
| "프로토타입이다" | 프로토타입이 프로덕션이 된다. 버릴 코드라면 어차피 삭제 비용은 없다. |

## 체크리스트

- [ ] 적용 대상인지 판단했다
- [ ] 실패하는 테스트를 실행했고, 실패 이유가 기능 미구현이다
- [ ] 최소 코드로 신규+기존 테스트가 모두 통과한다
- [ ] 리팩터링 후에도 green이다
- [ ] 테스트 전에 쓴 프로덕션 코드가 남아 있지 않다

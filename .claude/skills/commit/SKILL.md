# Commit 스킬

변경사항을 분석해 논리적 단위로 분류하고, 한국어 커밋 메시지로 커밋한다.

## 절차

### 1. 변경사항 분석
다음 명령을 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 스타일 참고 (커밋이 없으면 생략)
```

- untracked 파일은 내용을 읽어 목적을 파악한다.
- `.env`, 키, 토큰 등 비밀 정보나 `node_modules`, 빌드 산출물이 포함되어 있으면 커밋 대상에서 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류
- 하나의 커밋은 하나의 목적만 가진다 (기능 추가, 버그 수정, 리팩터링, 설정 변경을 섞지 않는다).
- 서로 관련 없는 변경은 별도 커밋으로 나눈다.
- 각 단위에 포함될 파일 목록을 정리한다.

### 3. 커밋 메시지 작성
형식:

```
<type>: <한국어 요약>

(선택) 본문: 무엇을/왜 변경했는지
```

| type | 용도 |
|------|------|
| feat | 새로운 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 코드 개선 |
| chore | 빌드, 설정, 의존성, 기타 잡무 |

규칙:
- 요약은 한국어로, 50자 내외, 마침표 없이 작성한다.
- "무엇을 했는지"가 드러나는 명사형/동사형 어미로 간결하게 쓴다. (예: `feat: 컴포넌트 생성 폼 추가`)
- 본문은 변경 이유가 자명하지 않을 때만 추가한다.
- 위 4가지에 맞지 않는 경우(docs, test, style 등)는 가장 가까운 타입을 쓰거나 사용자에게 확인한다.

### 4. 커밋 실행
**기본은 승인 없이 바로 커밋한다.** 커밋 단위별로 실행한다.

```bash
git add <해당 파일들>        # `git add -A`/`.` 대신 파일을 명시
git commit -m "<메시지>"
```

- 모든 커밋 후 `git log --oneline -n <커밋 수>`로 커밋 목록과 파일 구성을 보고한다.
- 커밋 전에 계획(단위별 메시지·파일 목록)을 한 번 출력해 무엇을 커밋하는지 남긴다.

#### 승인은 사용자가 요청할 때만
- 사용자가 "확인하고 커밋", "먼저 보여줘" 등 확인을 명시적으로 요청한 경우에만 계획을 보여주고 승인을 받는다.
- 그 외에는 묻지 않고 진행한다. 분류가 모호하면 가장 합리적인 단위로 나누어 커밋하고, 비밀 정보 의심 파일은 묻지 않고 제외한 뒤 보고에 알린다.

## 금지 사항
- 비밀 정보(`.env`, 키, 토큰)와 빌드 산출물은 승인 여부와 관계없이 커밋하지 않는다
- `git push`는 명시적으로 요청받기 전까지 실행하지 않는다
- `--no-verify`, `--amend`, `--force` 등은 요청 없이 사용하지 않는다
- pre-commit hook이 실패하면 원인을 수정한 뒤 새 커밋을 만든다
